# Agent.md

## Mission

Solve the provided heuristic optimization problem as effectively as possible under the contest constraints.

The final submission must be a single Python program that reads one instance from standard input and prints a valid sequence of stamp operations.

The main objective is to maximize the official score:

\[
P=\left\lfloor \frac{10^6 M}{N^2} \right\rfloor,
\]

where \(M\) is the number of cells in the final grid that match the target grid.

Do not optimize for elegance. Optimize for measured score, correctness, robustness, and contest usability.

---

## Core Rules

1. All solver implementations must be written in Python.
2. Never claim an improvement without measuring it using the local evaluator.
3. The first thing to build is the testing and scoring infrastructure.
4. Keep every meaningful best-performing solver as a separate submission-ready Python file.
5. Save a submission-ready checkpoint:
   - for the initial valid baseline, and
   - every time the measured benchmark score strictly improves.
6. Never overwrite old best checkpoints.
7. Every saved submission checkpoint must be self-contained and must not depend on local helper modules, generated files, benchmark data, or external packages that are unavailable in the judge environment.
8. The official output constraints must always be respected:
   - \(0 \le L \le K\)
   - \(0 \le x_i,y_i \le N-D\)
   - \(0 \le r_i \le 3\)
   - no extra output tokens
   - output size at most 100,000 bytes.
9. Prefer deterministic behavior for benchmark comparisons unless randomness is explicitly controlled by fixed seeds.
10. Do not use benchmark-specific hardcoding.

## Phase 1: Build the Evaluation Infrastructure First

Before serious solver work, implement and test the following.

### 1. Simulator

Create a canonical simulator that:

- parses one problem instance,
- accepts a list of operations,
- applies operations exactly according to the statement,
- returns the final grid and final stamp,
- can compute the number of matching cells.

Use this simulator as the single source of truth for local evaluation.

Add internal consistency tests for all four rotations for both `D=2` and `D=3`.

### 2. Output Validator

Implement validation for:

- operation count,
- coordinate ranges,
- rotation range,
- output token count,
- output size,
- integer parsing.

Invalid output must be detected before scoring.

### 3. Score Checker

Implement the exact official score:

```python
score = (1_000_000 * matches) // (N * N)
```

Report at least:

- matching cells,
- total cells,
- per-instance score,
- total benchmark score,
- average score.

### 4. Testcase Generator

Create a reproducible testcase generator covering the full constraint range:

- `3 <= N <= 30`
- `D in {2, 3}`
- `2 <= C <= 6`
- `1 <= K <= 180`

Use fixed seeds.

The generator must include both random and structured distributions, for example:

- fully independent random `A`, `T`, and `S`,
- `T` close to `A`,
- `T` generated by applying random legal operations to `A`,
- low-color-count cases,
- high-color-count cases,
- small `K`,
- large `K`,
- small `N`,
- large `N`,
- repetitive/checkerboard/striped target patterns,
- stamp distributions with repeated colors,
- nearly uniform grids,
- adversarial-looking local mismatches.

The purpose is not to imitate the hidden tests perfectly, but to avoid optimizing to one narrow distribution.

### 5. Benchmark Set

Construct a stable benchmark suite using fixed seeds.

Keep the benchmark unchanged while comparing solver revisions.

Recommended benchmark structure:

- a small smoke set for very fast iteration,
- a medium development set,
- a larger stable evaluation set.

For example:

- smoke: 20 cases,
- development: 100 cases,
- stable benchmark: 300+ cases if runtime allows.

Store the seeds/configuration so results are reproducible.

### 6. Benchmark Runner

The benchmark runner should:

- execute a solver on each case,
- validate its output,
- score it,
- enforce a reasonable timeout,
- aggregate results,
- print a concise summary,
- save machine-readable results,
- optionally show score breakdowns by:
  - `D`,
  - `C`,
  - `N` bucket,
  - `K` bucket,
  - testcase family.

## Phase 2: Establish an Initial Baseline

Before advanced optimization, create a simple valid baseline solver.

At minimum compare:

- zero operations,
- best single immediate operation,
- simple greedy repeated best-immediate operation.

The initial solver may be weak. It must be correct and measurable.

As soon as there is a valid baseline:

1. benchmark it,
2. record the score,
3. save a self-contained copy under `submissions/`,
4. mark it as the initial submission checkpoint.

This initial checkpoint is mandatory even if its score is poor.

---

## Phase 3: Iterative Score Optimization

After the infrastructure and initial checkpoint exist, repeatedly improve the solver.

Every iteration must follow:

1. Form a concrete hypothesis.
2. Modify the solver.
3. Run smoke tests.
4. Run the stable benchmark if smoke tests are promising.
5. Compare against the current best.
6. Record:
   - hypothesis,
   - implementation summary,
   - benchmark score,
   - score delta,
   - runtime,
   - observations.
7. If and only if the stable benchmark score strictly improves:
   - update the best score,
   - copy the solver into a new immutable submission file,
   - record the checkpoint in history.

Do not silently replace the previous best.

## Required Submission-Readiness Check

Before saving any checkpoint, verify that the file:

- is a single Python file,
- reads from `sys.stdin`,
- writes only the required answer to `sys.stdout`,
- has no debug output,
- does not read local files,
- does not import local modules,
- does not require third-party libraries,
- respects `K`,
- emits legal operations,
- completes within a contest-appropriate runtime,
- works for minimum and maximum constraints.

Run randomized differential checks against the canonical simulator whenever simulator logic is duplicated inside the solver.

## Solver Research Directions

Explore several approaches rather than only tuning one greedy rule.

### State and Delta Evaluation

Since `D` is only 2 or 3, each operation touches at most 9 grid cells.

Exploit this aggressively.

Maintain:

- current grid,
- current stamp,
- current number of matches,
- local match deltas.

The immediate score delta of an operation can be evaluated in \(O(D^2)\).

There are at most:

\[
4(N-D+1)^2
\]

legal placements per step, which is manageable for moderate evaluation strategies.

### Greedy Search

Useful baselines:

- choose the operation with maximum immediate gain,
- allow zero-gain moves if they improve stamp contents,
- evaluate immediate grid gain plus a heuristic value for the resulting stamp,
- restrict candidates to regions containing mismatches.

### Stamp-Aware Heuristics

The stamp is a mobile \(D \times D\) memory buffer.

A move can be useful even if it temporarily reduces matches, because it changes the colors carried by the stamp.

Consider heuristics based on:

- how many stamp cells already match colors needed near a candidate region,
- the multiset of colors currently on the stamp,
- local target color demand,
- whether a move collects useful colors for future placements,
- whether it destroys difficult-to-repair matched cells.

### Candidate Pruning

Potential filters:

- regions containing at least one mismatch,
- regions where the target colors overlap well with current stamp colors under some rotation,
- top candidates by cheap approximate delta,
- deduplicate equivalent rotations when stamp symmetries make them identical.

### Lookahead

Test shallow search such as:

- greedy with 2-ply lookahead,
- beam search,
- top-`B` first moves followed by best second move,
- limited Monte Carlo rollouts,
- short simulated annealing over operation sequences.

Always evaluate runtime versus score.

### Sequence Optimization

An operation sequence can be improved after construction.

Possible techniques:

- delete operations whose removal improves final score,
- truncate weak suffixes,
- replace one operation with another,
- replace short subsequences,
- local search on coordinates/rotations,
- re-simulate only affected suffixes when practical.

### Reverse or Target-Oriented Thinking

Investigate whether useful local structures arise from thinking about target patches as desired outgoing stamp states.

Because every operation is a swap, information is conserved across grid plus stamp. This may permit useful matching or routing interpretations.

Do not assume such ideas help; benchmark them.

### Randomization

If using stochastic search:

- use deterministic seeds during comparison,
- benchmark across multiple solver seeds if variance is high,
- do not accept an improvement based on a lucky single run.

The final submission may derive its seed deterministically from the input.

### Runtime Budgeting

The hidden runtime limit may punish excessive search.

Prefer techniques with controllable cost.

Measure:

- average runtime,
- worst-case runtime on generated max-size cases.

A slower approach must earn enough score to justify its cost.

## Experimental Discipline

### Do

- keep benchmark seeds fixed,
- measure every material change,
- keep notes,
- use ablations,
- test edge cases,
- profile bottlenecks,
- retain previous best submissions,
- compare both total score and per-family behavior.

### Do Not

- accept changes based on intuition alone,
- tune solely on one testcase,
- modify the benchmark after every poor result,
- delete old best solvers,
- accidentally benchmark with different random seeds,
- let debugging output enter submission files,
- use invalid approximations of the stamp rotation/state update.

---

## Acceptance Criterion for an Improvement

A solver revision counts as a new best only if:

1. it is valid on all benchmark cases,
2. its stable benchmark total score is strictly greater than the previous best,
3. its runtime remains acceptable,
4. the result is reproducible.

If score ties, keep the existing best unless the new solver is materially faster or simpler. Such a tie does not require a new best-score checkpoint.

## Final Deliverables

Maintain at all times:

- `tools/` with working generator, simulator, validator, scorer, and benchmark runner,
- `solvers/current.py` with the latest experiment,
- `submissions/` containing the initial checkpoint and every strict score improvement,
- `results/history.csv`,
- `notes/experiments.md`.

At the end, identify the best submission-ready Python file by measured stable benchmark score.

Do not present an unmeasured experimental solver as the final answer.
