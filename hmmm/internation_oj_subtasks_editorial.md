# 인터내셔널 OJ — OI형 서브태스크 설계 및 풀이

## 1. 결론

이 문제는 **의미 있는 OI형 서브태스크를 구성하기에 적합하다.**

전체 문제의 난점이 다음 다섯 단계로 비교적 명확하게 분리되기 때문이다.

1. 서버 큐에서 각 제출의 **채점 완료 시각을 계산**한다.
2. 여러 서버에서 발생하는 완료 이벤트를 **전역 시간순으로 병합**한다.
3. 문제마다 정렬 기준에 따른 **상위 5개 제출**을 유지한다.
4. 사용자별 푼 문제 수가 바뀔 때 **전역 사용자 랭킹**을 갱신한다.
5. 같은 사용자가 같은 문제를 여러 번 제출한 경우를 **중복 제거**한다.

따라서 단순히 제한만 작게 만드는 서브태스크보다, 위 난점을 하나씩 드러내는 방식으로 배치하는 것이 좋다.

---

## 2. 권장 서브태스크 구성

각 서브태스크는 독립 채점 그룹을 가정한다.

| 서브태스크 | 배점 | 추가 제한 | 주로 확인하는 핵심 |
|---|---:|---|---|
| 1 | 10 | $Q \le 2\,000$ | 완전탐색으로 문제 정의 이해 |
| 2 | 12 | $N=1$, `3`번 쿼리 없음 | 완료 시각 계산, 문제별 상위 5개 |
| 3 | 18 | `3`번 쿼리 없음 | 여러 서버의 완료 이벤트 병합 |
| 4 | 15 | $N=1$, `2`번 쿼리 없음, 각 `(닉네임, 문제 번호)` 쌍은 최대 한 번 제출 | 사용자 랭킹의 동적 갱신 |
| 5 | 20 | 각 `(닉네임, 문제 번호)` 쌍은 최대 한 번 제출 | 두 랭킹 구조의 결합 |
| 6 | 25 | 추가 제한 없음 | 중복 제출까지 포함한 전체 문제 |

총점은 100점이다.

### 이 구성이 의미 있는 이유

- 서브태스크 2에서 참가자는 먼저 **서버 하나의 완료 이벤트가 제출 순서와 같음**을 이용한다.
- 서브태스크 3에서는 서버가 여러 개가 되면서 완료 순서가 입력 순서와 달라지므로 **최소 힙**이 자연스럽게 등장한다.
- 서브태스크 4는 문제별 랭킹을 제거하여, 별도의 핵심인 **사용자 랭킹의 삭제 후 재삽입**에 집중하게 한다.
- 서브태스크 5에서는 두 종류의 랭킹이 서로 거의 독립적으로 관리된다는 점을 확인한다.
- 마지막 서브태스크는 같은 문제의 재제출이 푼 문제 수를 늘리지 않는다는 조건만 추가한다. 이때 **완료된 `(사용자, 문제)` 쌍 집합**이 필요하다.

### 권장하지 않는 서브태스크

다음 제한은 구현량만 줄이거나 상수만 바꿀 뿐, 핵심 알고리즘에 대한 힌트가 약하다.

- 문제 번호 $x$의 범위를 작게 제한하기
- 채점 시간 $y$ 또는 시각 $t$의 범위를 작게 제한하기
- 출력 개수를 5개에서 1개로 바꾸기
- $N \le 10$처럼 서버 수만 조금 줄이기

특히 $N$이 2 이상인 순간 완료 이벤트의 전역 순서는 여전히 입력 순서와 달라질 수 있으므로, $N \le 10$은 핵심 난점을 제거하지 못한다. 반면 $N=1$은 완료 순서 자체가 단순해지므로 의미가 있다.

## 3. 모든 풀이의 출발점: 완료 시각을 즉시 계산하기

서버 $i$에 지금까지 들어온 마지막 제출의 완료 시각을 $F_i$라고 하자.

시각 $t$에 채점 시간 $y$인 새 제출이 서버 $i$에 들어오면 시작 시각과 완료 시각은 다음과 같다.

\[
\text{start}=\max(t,F_i),
\qquad
\text{finish}=\max(t,F_i)+y.
\]

그리고

\[
F_i \leftarrow \text{finish}
\]

로 갱신한다.

입력 쿼리의 시각이 감소하지 않으며 각 서버가 FIFO로 처리하므로, 서버의 실제 큐를 저장할 필요가 없다. 서버마다 마지막 완료 시각 하나만 있으면 모든 제출의 완료 시각을 입력 시점에 확정할 수 있다.

완료 시각의 최댓값은 대략 $2\times 10^{14}$까지 커질 수 있으므로 64비트 정수를 사용해야 한다.

# 4. 서브태스크별 풀이

## 서브태스크 1: $Q \le 2\,000$

### 의도

문제의 두 랭킹 정의와 완료 시각 계산을 정확히 이해했는지 확인한다.

### 풀이

`1`번 쿼리가 들어올 때 위 점화식으로 완료 시각을 계산하고 모든 제출을 배열에 저장한다.

`2 t x` 쿼리에서는 다음 조건을 만족하는 제출을 모두 모은다.

- 문제 번호가 $x$
- 완료 시각이 $t$ 이하

그 후 다음 키로 정렬한다.

\[
(\text{채점 시간},\ \text{완료 시각},\ \text{제출 쿼리 순서})
\]

앞에서 최대 5개를 출력한다.

`3 t` 쿼리에서는 완료 시각이 $t$ 이하인 제출만 보면서 다음을 다시 계산한다.

1. 각 `(사용자, 문제)` 쌍의 최초 완료 시각을 구한다.
2. 사용자별 서로 다른 문제 수를 센다.
3. 사용자가 현재 푼 문제 수를 달성한 시각은 각 문제의 최초 완료 시각 중 최댓값이다.
4. 다음 키로 사용자를 정렬한다.

\[
(-\text{푼 문제 수},\ \text{달성 시각},\ \text{닉네임})
\]

### 시간 복잡도

출력 쿼리마다 모든 제출을 다시 조사하고 정렬하면 대략

\[
O(Q^2\log Q)
\]

이다. $Q\le 2\,000$에서는 충분하다.

### 전체 풀이로 이어지는 힌트

완전탐색을 구현하면 두 랭킹 모두 **완료된 제출이 추가될 때만 상태가 변한다**는 사실을 발견할 수 있다. 전체 풀이에서는 매 출력 쿼리마다 재계산하지 않고 완료 이벤트가 발생할 때만 자료구조를 갱신한다.

## 서브태스크 2: $N=1$, `3`번 쿼리 없음

### 의도

사용자 랭킹을 제거하고, 한 서버에서 발생하는 완료 이벤트와 문제별 랭킹 관리에 집중한다.

### 핵심 관찰

서버가 하나이면 제출 완료 시각은 제출 쿼리 순서대로 엄격히 증가한다. 채점 시간이 항상 양수이기 때문이다.

따라서 아직 반영하지 않은 완료 이벤트를 큐에 넣어 두고, 시각 $t$의 쿼리를 처리하기 전에 큐 앞에서 완료 시각이 $t$ 이하인 이벤트를 모두 꺼내면 된다.

### 문제별 상위 5개 유지

문제 랭킹의 키는 다음과 같다.

\[
(\text{채점 시간},\ \text{완료 시각},\ \text{제출 쿼리 순서})
\]

각 문제에 대해 상위 5개만 필요하다. 완료된 제출 하나를 추가할 때 다음처럼 처리할 수 있다.

1. 해당 문제의 벡터에 새 기록을 삽입한다.
2. 벡터를 정렬한다.
3. 크기가 6이면 마지막 원소를 제거한다.

벡터의 크기는 항상 최대 5이므로 정렬 비용은 상수로 볼 수 있다.

한 번 상위 5개에서 밀려난 기록은 이후 새 기록이 추가되어도 다시 상위 5개로 돌아올 수 없다. 모든 랭킹 키가 고정되어 있고 삭제가 없기 때문이다.

### 시간 복잡도

각 제출과 완료 이벤트를 한 번씩 처리하므로

\[
O(Q)
\]

으로 해결할 수 있다. 해시 맵의 연산은 평균 $O(1)$로 본다.

### 전체 풀이로 이어지는 힌트

서버가 여러 개이면 각 서버 내부의 완료 순서는 정렬되어 있지만, 서버 사이의 완료 순서는 섞인다. 즉, 여러 정렬된 이벤트 열을 전역 시간순으로 합치는 구조가 필요하다.

---

## 서브태스크 3: `3`번 쿼리 없음

### 의도

여러 서버의 완료 이벤트를 시간순으로 처리하는 방법을 유도한다.

### 왜 입력 순서대로 완료되지 않는가

예를 들어 다음 두 제출을 생각하자.

- 서버 1: 시각 0에 채점 시간 100인 제출
- 서버 2: 시각 1에 채점 시간 1인 제출

두 번째 제출이 나중에 입력되지만 시각 2에 먼저 완료된다.

따라서 제출 배열을 입력 순서대로 훑는 것만으로는 시각 $t$까지 완료된 제출을 찾을 수 없다.

### 최소 힙

각 `1`번 쿼리에서 완료 시각을 계산한 뒤 다음 정보를 최소 힙에 넣는다.

- 완료 시각
- 문제 번호
- 채점 시간
- 제출자
- 제출 쿼리 순서

각 쿼리의 시각이 $t$일 때, 실제 쿼리 내용을 처리하기 전에

```text
while 힙이 비어 있지 않고 최소 완료 시각 <= t:
    완료 이벤트를 하나 꺼낸다.
    문제별 상위 5개에 반영한다.
```

를 수행한다.

이렇게 하면 `2 t x`가 실행되는 순간 자료구조에는 정확히 시각 $t$까지 완료된 제출만 반영되어 있다.

### 시간 복잡도

각 제출은 힙에 한 번 들어가고 한 번 나오므로

\[
O(Q\log Q)
\]

이다.

### 전체 풀이로 이어지는 힌트

전체 문제에서도 완료 이벤트를 꺼내는 부분은 그대로 사용한다. 달라지는 것은 완료 이벤트 하나를 처리할 때 문제 랭킹뿐 아니라 사용자 랭킹도 함께 갱신한다는 점뿐이다.

## 서브태스크 4: $N=1$, `2`번 쿼리 없음, `(사용자, 문제)` 중복 제출 없음

### 의도

완료 이벤트 병합과 문제별 랭킹을 제거하고, 사용자 랭킹의 동적 갱신만 분리해 연습하게 한다.

### 사용자 상태

각 사용자 $u$에 대해 다음 두 값을 저장한다.

- $C_u$: 현재 푼 문제 수
- $A_u$: 현재 푼 문제 수를 달성한 시각

이 서브태스크에서는 같은 `(사용자, 문제)` 쌍이 한 번만 제출되므로, 그 제출이 완료될 때마다 반드시 새로운 문제를 하나 푼다.

따라서 완료 시각이 $f$인 이벤트를 처리하면

\[
C_u \leftarrow C_u+1,
\qquad
A_u \leftarrow f
\]

이다.

### 전역 사용자 랭킹

사용자 랭킹 키는 다음과 같다.

\[
(-C_u,\ A_u,\ \text{닉네임})
\]

균형 이진 탐색 트리인 `std::set`에 이 키를 넣는다.

사용자의 상태가 바뀔 때는 반드시 다음 순서로 처리한다.

1. 사용자가 이미 랭킹에 있다면 이전 키를 삭제한다.
2. $C_u$, $A_u$를 갱신한다.
3. 새 키를 삽입한다.

`3`번 쿼리에서는 집합의 앞에서 최대 5개를 출력한다.

### 왜 단순 우선순위 큐만으로는 불편한가

사용자가 새 문제를 풀 때마다 기존 랭킹 키가 무효가 된다. 우선순위 큐에 새 키만 추가하는 지연 삭제도 가능하지만, 출력할 때 오래된 키를 판별하는 추가 장치가 필요하다.

이 문제에서는 `set`으로 이전 키를 직접 지우고 새 키를 넣는 방식이 더 단순하다.

### 시간 복잡도

각 새 문제 완료마다 집합에서 삭제와 삽입을 한 번씩 수행하므로

\[
O(Q\log Q)
\]

이다.

### 전체 풀이로 이어지는 힌트

전체 문제에서는 완료된 제출이 항상 새 문제를 의미하지 않는다. 상태 갱신 전에 `(사용자, 문제)`가 이미 완료된 적이 있는지 검사하면 된다.

---

## 서브태스크 5: `(사용자, 문제)` 중복 제출 없음

### 의도

지금까지의 모든 자료구조를 결합하되, 중복 제출 판정만 제거한다.

### 풀이

다음 구조를 동시에 유지한다.

1. `serverFinish[i]`
   - 서버별 마지막 완료 시각
2. 완료 이벤트 최소 힙
   - 여러 서버의 완료 이벤트를 전역 시간순으로 처리
3. 문제별 최대 5개 기록
   - 키 `(채점 시간, 완료 시각, 제출 순서)`
4. 사용자별 `solvedCount`, `achievedTime`
5. 전역 사용자 랭킹 `set`
   - 키 `(-푼 문제 수, 달성 시각, 닉네임)`

완료 이벤트 하나를 꺼낼 때 다음 두 갱신은 서로 독립적이다.

- 문제별 상위 5개 갱신
- 해당 사용자의 사용자 랭킹 키 갱신

### 시간 복잡도

\[
O(Q\log Q)
\]

이다.

### 전체 풀이로 이어지는 힌트

전체 제한에서는 사용자 랭킹 갱신을 모든 완료 이벤트에 대해 수행하면 안 된다. 같은 문제를 이미 푼 사용자는 문제 랭킹에는 새 기록이 추가되지만, 사용자 랭킹은 바뀌지 않는다.

---

## 서브태스크 6: 전체 제한

서브태스크 5의 구조에 **완료된 `(사용자, 문제)` 쌍의 집합**만 추가한다.

완료 이벤트 `(u,x)`를 처리할 때 다음처럼 나눈다.

- 문제별 랭킹에는 항상 기록을 추가한다.
- `(u,x)`가 집합에 처음 삽입되는 경우에만 사용자 랭킹을 갱신한다.

중요한 점은 제출 시점이 아니라 **완료 이벤트 처리 시점**에 중복 여부를 검사해야 한다는 것이다. 같은 사용자가 같은 문제를 여러 번 제출했을 때, 나중에 제출한 기록이 더 먼저 완료될 수도 있기 때문이다.

# 5. 전체 풀이

## 5.1 유지할 정보

### 서버별 정보

```text
serverFinish[i] = 서버 i에 현재 들어가 있는 마지막 제출의 완료 시각
```

### 완료 이벤트 최소 힙

각 이벤트는 다음 정보를 가진다.

```text
(finishTime, judgeTime, problem, user, submissionOrder)
```

힙은 `finishTime`이 작은 이벤트부터 꺼낸다. 같은 완료 시각 이벤트의 처리 순서는 최종 상태에 영향을 주지 않지만, 구현을 결정적으로 만들기 위해 제출 순서를 보조 키로 둘 수 있다.

### 문제별 상위 5개

각 문제 번호마다 최대 5개의 기록만 정렬된 벡터로 저장한다.

기록의 비교 키는

```text
(judgeTime, finishTime, submissionOrder)
```

이다.

닉네임은 비교 기준이 아니므로, 출력에 사용할 사용자 ID만 함께 저장하면 된다.

### 완료된 `(사용자, 문제)` 쌍

해시 집합에 `(userId, problemNumber)`를 저장한다.

완료 이벤트를 처리할 때 처음 등장한 쌍인지 판정한다.

### 사용자별 상태와 전역 랭킹

각 사용자마다 다음을 저장한다.

```text
solvedCount[user]
achievedTime[user]
```

전역 집합의 키는

```text
(-solvedCount, achievedTime, nickname)
```

이다.

푼 문제가 0개인 사용자는 집합에 넣지 않는다.

## 5.2 쿼리 처리 순서

모든 쿼리는 다음 공통 전처리를 먼저 한다.

```text
processUntil(t):
    while 완료 이벤트 힙의 최솟값.finishTime <= t:
        이벤트를 꺼내 랭킹에 반영
```

그 후 쿼리 종류별 처리를 한다.

### `1 t i x y s`

```text
start  = max(t, serverFinish[i])
finish = start + y
serverFinish[i] = finish

완료 이벤트 (finish, y, x, s, 현재 쿼리 순서)를 힙에 삽입
```

채점 시간 $y\ge1$이므로 새로 삽입한 제출이 같은 시각 $t$에 완료되는 경우는 없다.

### `2 t x`

`processUntil(t)`가 끝난 뒤에는 문제 $x$의 벡터가 이미 정답이다. 앞에서 최대 5개를 출력한다.

### `3 t`

`processUntil(t)`가 끝난 뒤에는 전역 사용자 랭킹 집합이 이미 정답이다. 집합의 앞에서 최대 5명을 출력한다.

## 5.3 완료 이벤트 처리

완료 이벤트

```text
(finish, judgeTime, problem, user, order)
```

를 하나 꺼냈다고 하자.

### 1단계: 문제 랭킹 갱신

```text
problemTop5[problem]에 기록 추가
정렬
크기가 6이면 마지막 기록 제거
```

모든 완료 제출은 같은 사용자의 재제출이어도 서로 다른 기록이므로 항상 추가한다.

### 2단계: 사용자 랭킹 갱신 여부 판정

`(user, problem)`을 완료 쌍 집합에 삽입한다.

이미 존재하던 쌍이면 아무것도 하지 않는다.

처음 등장한 쌍이면 다음을 수행한다.

```text
기존 solvedCount > 0이면 전역 랭킹에서 이전 키 삭제
solvedCount += 1
achievedTime = finish
새 키 삽입
```

여러 새 문제가 같은 시각에 완료되면 갱신 순서와 관계없이 마지막 상태의 `achievedTime`은 그 동일한 완료 시각이 된다.

# 6. 정당성 증명

## 보조정리 1. 각 제출에 대해 계산한 완료 시각은 실제 완료 시각과 같다.

서버 $i$의 직전 마지막 제출 완료 시각을 $F_i$라고 하자.

새 제출은 도착 시각 $t$보다 먼저 시작할 수 없고, 직전 제출이 끝나는 $F_i$보다 먼저 시작할 수도 없다. 따라서 시작 시각은 $\max(t,F_i)$이다.

채점에 정확히 $y$만큼 걸리므로 완료 시각은 $\max(t,F_i)+y$이다. FIFO 처리에 의해 이 뒤에 들어오는 제출도 이 완료 시각 이후에만 시작할 수 있으므로 `serverFinish[i]`를 이 값으로 바꾸는 것이 정확하다. ∎

## 보조정리 2. `processUntil(t)`가 끝나면 시각 $t$까지 완료된 제출만, 그리고 그 모든 제출이 자료구조에 반영되어 있다.

모든 제출은 보조정리 1에서 구한 실제 완료 시각을 키로 최소 힙에 들어간다.

`processUntil(t)`는 완료 시각이 $t$ 이하인 이벤트를 모두 꺼내며, 힙의 최솟값이 $t$보다 커지는 순간 멈춘다. 따라서 완료 시각이 $t$ 이하인 모든 이벤트는 처리되고, $t$보다 큰 이벤트는 하나도 처리되지 않는다. ∎

## 보조정리 3. 각 문제의 벡터에는 현재까지 완료된 제출 중 랭킹이 가장 높은 최대 5개가 정렬되어 저장된다.

완료 이벤트를 처리하기 전 이 성질이 성립한다고 가정하자.

새 기록을 추가한 뒤 기존 최대 5개와 새 기록, 최대 6개만 비교하면 된다. 기존에 5위 밖이어서 버린 기록은 기존 5개보다 낮고, 이후에는 기록이 추가되기만 하므로 다시 5위 안으로 들어올 수 없다.

6개를 정렬한 뒤 가장 낮은 하나를 제거하면 새 전체 집합의 상위 5개가 정확히 남는다. 수학적 귀납법에 의해 항상 성립한다. ∎

## 보조정리 4. 사용자 `solvedCount`와 `achievedTime`은 현재 완료된 제출을 기준으로 정확하다.

완료된 `(사용자, 문제)` 쌍을 집합으로 관리하므로, 사용자가 같은 문제를 여러 번 완료해도 최초 한 번만 `solvedCount`가 증가한다. 반대로 새로운 문제의 첫 완료 이벤트는 집합에 존재하지 않으므로 정확히 한 번 증가한다.

새 문제를 처음 푼 이벤트를 완료 시각 순으로 처리하므로, 가장 최근 증가에서 기록한 완료 시각이 곧 현재 푼 문제 수를 달성한 시각이다. 같은 시각에 여러 문제가 처음 완료되어도 그 시각은 동일하므로 결과는 변하지 않는다. ∎

## 보조정리 5. 전역 사용자 랭킹 집합은 현재 랭킹에 포함되는 모든 사용자의 정확한 키를 하나씩 가진다.

사용자가 처음 문제를 풀면 새 키를 삽입한다. 이후 새 문제를 풀 때는 이전 키를 삭제한 뒤 갱신된 키를 삽입한다. 같은 문제의 재완료에는 아무 변화가 없다.

따라서 푼 문제가 하나 이상인 각 사용자는 정확히 하나의 최신 키를 가지며, 푼 문제가 없는 사용자는 포함되지 않는다. 집합의 정렬 순서는 문제에서 정의한 사용자 랭킹 순서와 같다. ∎

## 정리. 알고리즘은 모든 `2`번과 `3`번 쿼리에 올바른 답을 출력한다.

보조정리 2에 의해 출력 직전 자료구조에는 정확히 시각 $t$까지 완료된 제출만 반영된다.

보조정리 3에 의해 `2`번 쿼리에서 문제별 벡터의 앞 최대 5개가 정확한 문제 랭킹이다.

보조정리 4와 5에 의해 `3`번 쿼리에서 전역 집합의 앞 최대 5개가 정확한 사용자 랭킹이다. ∎

# 7. 복잡도 분석

각 제출은 완료 이벤트 힙에 한 번 들어가고 한 번 나온다.

- 완료 이벤트 힙: 전체 $O(Q\log Q)$
- 사용자 랭킹 집합 갱신: 새 `(사용자, 문제)` 쌍마다 $O(\log Q)$
- 문제별 상위 5개 갱신: 벡터 크기가 최대 6이므로 $O(1)$
- 출력: 쿼리당 최대 5개이므로 $O(1)$

따라서 전체 시간 복잡도는

\[
O(Q\log Q)
\]

이고, 공간 복잡도는

\[
O(Q)
\]

이다.

# 8. 구현 시 주의할 점

1. **완료 시각은 `long long`**
   - 한 서버에 채점 시간 $10^9$인 제출이 $2\times10^5$개 쌓일 수 있다.

2. **완료 이벤트는 모든 쿼리 시작 전에 처리**
   - 완료 시각이 쿼리 시각과 같은 제출도 결과에 포함되어야 한다.

3. **문제 랭킹과 사용자 랭킹의 갱신 조건이 다름**
   - 문제 랭킹: 모든 완료 제출을 추가
   - 사용자 랭킹: 새로운 `(사용자, 문제)`일 때만 갱신

4. **문제 랭킹의 세 번째 비교 키는 제출 쿼리 순서**
   - 닉네임 순서가 아니다.

5. **사용자 랭킹의 달성 시각은 마지막 제출 시각이 아님**
   - 사용자가 새로운 문제를 처음 푼 가장 최근 완료 시각이다.
   - 이미 푼 문제를 다시 제출해 완료해도 바뀌지 않는다.

6. **동일 완료 시각의 이벤트 순서는 중요하지 않음**
   - 문제 랭킹은 제출 순서를 별도 키로 저장한다.
   - 사용자 랭킹은 같은 시각의 여러 새 문제 완료 후 달성 시각이 모두 동일하다.

7. **닉네임을 사용자 ID로 압축**
   - 이벤트와 문제별 기록에는 문자열 대신 정수 ID를 저장하면 메모리를 줄일 수 있다.

# 9. C++17 참고 구현

```cpp
#include <bits/stdc++.h>
using namespace std;

using int64 = long long;
using uint64 = unsigned long long;

struct SplitMix64Hash {
    static uint64 splitmix64(uint64 x) {
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }

    size_t operator()(uint64 x) const {
        static const uint64 seed =
            chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + seed);
    }
};

struct Event {
    int64 finishTime;
    int64 judgeTime;
    int64 problem;
    int user;
    int order;
};

struct EventGreater {
    bool operator()(const Event& a, const Event& b) const {
        if (a.finishTime != b.finishTime) {
            return a.finishTime > b.finishTime;
        }
        return a.order > b.order;
    }
};

struct ProblemRecord {
    int64 judgeTime;
    int64 finishTime;
    int order;
    int user;
};

static bool problemRecordLess(const ProblemRecord& a,
                              const ProblemRecord& b) {
    if (a.judgeTime != b.judgeTime) {
        return a.judgeTime < b.judgeTime;
    }
    if (a.finishTime != b.finishTime) {
        return a.finishTime < b.finishTime;
    }
    return a.order < b.order;
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int N, Q;
    cin >> N >> Q;

    vector<int64> serverFinish(N + 1, 0);
    priority_queue<Event, vector<Event>, EventGreater> events;

    map<string, int> userId;
    vector<string> userName;
    vector<int> solvedCount;
    vector<int64> achievedTime;

    unordered_map<int64, vector<ProblemRecord>, SplitMix64Hash> problemTop5;
    problemTop5.reserve(Q * 2);

    unordered_set<uint64, SplitMix64Hash> solvedPair;
    solvedPair.reserve(Q * 2);

    // (-푼 문제 수, 현재 푼 문제 수 달성 시각, 닉네임)
    set<tuple<int, int64, string>> userRanking;

    auto getUserId = [&](const string& name) -> int {
        auto it = userId.find(name);
        if (it != userId.end()) {
            return it->second;
        }
        int id = static_cast<int>(userName.size());
        userId[name] = id;
        userName.push_back(name);
        solvedCount.push_back(0);
        achievedTime.push_back(0);
        return id;
    };

    auto processUntil = [&](int64 t) {
        while (!events.empty() && events.top().finishTime <= t) {
            Event e = events.top();
            events.pop();

            // 문제별 상위 5개 갱신
            auto& top = problemTop5[e.problem];
            top.push_back({e.judgeTime, e.finishTime, e.order, e.user});
            sort(top.begin(), top.end(), problemRecordLess);
            if (top.size() > 5) {
                top.pop_back();
            }

            // 사용자가 이 문제를 처음 푼 경우에만 사용자 랭킹 갱신
            uint64 pairKey = (uint64(static_cast<uint32_t>(e.user)) << 32)
                           | uint64(static_cast<uint32_t>(e.problem));
            if (solvedPair.insert(pairKey).second) {
                int oldCount = solvedCount[e.user];
                if (oldCount > 0) {
                    userRanking.erase({-oldCount,
                                       achievedTime[e.user],
                                       userName[e.user]});
                }

                ++solvedCount[e.user];
                achievedTime[e.user] = e.finishTime;
                userRanking.insert({-solvedCount[e.user],
                                    achievedTime[e.user],
                                    userName[e.user]});
            }
        }
    };

    for (int order = 0; order < Q; ++order) {
        int type;
        int64 t;
        cin >> type >> t;

        processUntil(t);

        if (type == 1) {
            int server;
            int64 problem, judgeTime;
            string name;
            cin >> server >> problem >> judgeTime >> name;

            int uid = getUserId(name);
            int64 startTime = max(t, serverFinish[server]);
            int64 finishTime = startTime + judgeTime;
            serverFinish[server] = finishTime;

            events.push({finishTime, judgeTime, problem, uid, order});
        } else if (type == 2) {
            int64 problem;
            cin >> problem;

            auto it = problemTop5.find(problem);
            if (it == problemTop5.end() || it->second.empty()) {
                cout << -1 << '\n';
                continue;
            }

            for (const ProblemRecord& record : it->second) {
                cout << userName[record.user] << ' '
                     << record.judgeTime << '\n';
            }
        } else {
            if (userRanking.empty()) {
                cout << -1 << '\n';
                continue;
            }

            int printed = 0;
            for (auto it = userRanking.begin();
                 it != userRanking.end() && printed < 5;
                 ++it, ++printed) {
                const auto& [negativeCount, time, name] = *it;
                cout << name << ' ' << -negativeCount << '\n';
            }
        }
    }

    return 0;
}
```

# 10. 출제 관점의 추가 제안

## 데이터 구성

서브태스크뿐 아니라 전체 데이터에도 다음 유형을 반드시 섞는 것이 좋다.

- 입력 순서와 완료 순서가 크게 뒤집히는 여러 서버
- 한 서버에 매우 긴 작업이 쌓인 뒤 늦게 들어온 다른 서버의 짧은 작업이 먼저 끝나는 경우
- 같은 문제에 채점 시간과 완료 시각이 모두 같은 제출 여러 개
- 같은 사용자가 같은 문제를 여러 서버에 반복 제출하여 나중 제출이 먼저 완료되는 경우
- 한 사용자가 같은 시각에 서로 다른 문제 여러 개를 처음 푸는 경우
- 사용자 여러 명이 같은 푼 문제 수와 같은 달성 시각을 가져 닉네임으로 순서가 정해지는 경우
- 문제와 사용자가 각각 $2\times10^5$개에 가까운 희소 데이터
- 출력 직전 시각과 정확히 같은 시각에 완료되는 제출

## 부분 점수 간 의존성

위 구성은 서브태스크 2와 4가 각각 문제 랭킹과 사용자 랭킹을 독립적으로 연습하게 하고, 서브태스크 3과 5가 이를 확장하도록 설계되어 있다.

다만 대회가 누적형 서브태스크만 허용한다면 다음처럼 단순화할 수 있다.

| 단계 | 추가 제한 |
|---|---|
| 1 | $Q\le2\,000$ |
| 2 | $N=1$, `(사용자, 문제)` 중복 없음 |
| 3 | $N=1$ |
| 4 | `(사용자, 문제)` 중복 없음 |
| 5 | 전체 제한 |

독립형 구성보다 각 핵심을 분리하는 효과는 약하지만, 제한을 하나씩 제거하는 자연스러운 누적 구조를 얻을 수 있다.

# 11. 핵심 요약

이 문제의 전체 풀이를 한 문장으로 요약하면 다음과 같다.

> 서버별 마지막 완료 시각으로 각 제출의 완료 시각을 즉시 구하고, 완료 이벤트를 최소 힙으로 시간순 처리하면서 문제별 상위 5개와 사용자 전역 랭킹을 갱신한다.

서브태스크는 이 문장을 다음 순서로 발견하도록 설계하는 것이 가장 교육적이다.

```text
완료 시각 계산
→ 한 서버의 이벤트 처리
→ 여러 서버 이벤트의 최소 힙 병합
→ 문제별 상위 5개
→ 사용자 랭킹의 삭제/재삽입
→ 완료된 (사용자, 문제) 중복 제거
```
