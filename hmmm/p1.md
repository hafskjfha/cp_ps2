# 인터네셔널 OJ

## 문제

J왕국에는 $N$개의 도시가 있다. 도시에는 $1,2,\dots,N$번의 번호가 붙어 있다.

도시들은 $M$개의 양방향 도로로 연결되어 있으며, 각 도로를 통과하는 데에는 일정한 시간이 필요하다. 임의의 두 도시 사이를 이동할 때 필요한 최소 시간을 두 도시 사이의 **거리**라고 하며, $\operatorname{dist}(i,j)$로 나타낸다.

J왕국의 도로에는 통신망이 연결되어 있다. 따라서 $i$번 도시에서 $j$번 도시로 전송되는 네트워크 요청이나 응답의 지연 시간은 $\operatorname{dist}(i,j)$이다.

J왕국에서 가장 유명한 온라인 저지인 **인터네셔널 OJ**는 다음과 같은 서버를 운영하고 있다.

* 웹 서버 $S$개 ($1 \le S \le N$)
* DB 서버 $D$개 ($1 \le D \le 2$)
* 채점 서버 $J$개 ($1 \le J \le 3$)

각 서버는 특정 도시에 존재한다. 같은 도시에 여러 종류의 서버가 존재할 수도 있다.

또한 $L$번 도시에는 모든 사용자 요청을 가장 먼저 받는 로드 밸런서가 존재한다.

DB에는 서비스에서 제공하는 문제 번호의 목록이 미리 저장되어 있다. 이 문제 목록은 문제를 처리하는 동안 바뀌지 않는다.

모든 DB 서버는 하나의 논리적인 DB를 공유한다. 따라서 어떤 DB 서버에 결과가 반영되면 같은 시각부터 모든 DB 서버에서 그 결과를 조회할 수 있다.

---

## 서버 선택 규칙

사용자가 $A$번 도시에서 요청을 보내면 로드 밸런서는 $A$번 도시와 가장 가까운 웹 서버에 요청을 전달한다.

거리가 같은 웹 서버가 여러 개라면 입력에서 먼저 주어진 웹 서버를 선택한다.

웹 서버가 DB 서버 또는 채점 서버를 선택할 때에도 같은 방식으로 자신과 가장 가까운 서버를 선택한다. 거리가 같다면 입력에서 먼저 주어진 서버를 선택한다.

채점 서버가 채점 결과를 기록할 DB 서버를 선택할 때에는 채점 서버와 가장 가까운 DB 서버를 선택한다. 거리가 같다면 입력에서 먼저 주어진 DB 서버를 선택한다.

웹 서버, DB 서버, 채점 서버에는 각각 입력 순서대로 $1$번부터 번호가 붙는다.

## 요청 시각과 웹 요청의 동기 처리

총 $Q$개의 요청이 입력 순서대로 주어진다. 각 요청에는 사용자가 요청을 보낸 시각 $t$가 함께 주어진다.

요청 시각은 양의 정수이며, 입력에서 엄격히 증가한다.

인터네셔널 OJ는 웹 요청을 한 번에 하나만 처리한다. 하나의 웹 요청 처리가 끝나기 전에는 다음 웹 요청의 처리를 시작하지 않는다.

$i$번째 요청의 입력 시각을 $t_i$, 실제 처리 시작 시각을 $s_i$, 처리 종료 시각을 $e_i$라고 하자. $e_0=0$으로 두면,

$$
s_i=\max(t_i,e_{i-1})
$$

이다. 즉, 사용자가 요청을 보낸 뒤 앞선 요청이 끝나지 않았다면, 해당 요청은 앞선 요청이 끝날 때까지 기다린 뒤 처리된다.

각 요청을 실제로 처리하기 직전에, 시각 $s_i$ 이하에 DB에 도착하도록 예정된 모든 채점 결과를 먼저 DB에 반영하고 필요한 캐시 무효화를 수행한다. 여러 채점 결과가 같은 시각에 DB에 도착한다면 해당 POST 요청이 입력으로 주어진 순서대로 반영한다.

따라서 시각 $s_i$에 DB에 도착한 결과는 $i$번째 요청에서 조회할 수 있다.

GET 요청의 응답 내용, 캐시 적중 여부, LRU 순서 변경 및 캐시 저장은 모두 실제 처리 시작 시각 $s_i$의 상태를 기준으로 하나의 작업처럼 처리된다. 그 뒤 네트워크 지연만큼 시간이 지나 응답이 사용자에게 도착하며, 이때 GET 요청의 처리가 끝난다.

GET 요청의 응답이 이동하는 동안 채점 결과가 DB에 반영되더라도 이미 결정된 응답 내용은 바뀌지 않는다. 단, 해당 DB 반영에 따른 캐시 무효화는 예정된 시각에 발생하며 이후 요청의 캐시 상태에는 반영된다.

POST 요청은 제출이 선택된 채점 서버의 큐에 도착할 때까지 웹 요청으로 처리한다. 제출이 채점 서버의 큐에 도착하면 POST 요청의 처리가 끝나며 다음 웹 요청을 처리할 수 있다. 그 이후의 큐 대기, 채점 및 DB 반영은 웹 요청 처리와 독립적으로 비동기 진행된다.

---

## 통신 시간

사용자가 $A$번 도시에서 보낸 요청은 다음 경로를 따라 이동한다.

$$
\text{사용자 도시 } A
\rightarrow
\text{로드 밸런서 } L
\rightarrow
\text{웹 서버 } W
$$

웹 서버가 사용자에게 응답할 때에는 웹 서버가 위치한 도시 $W$에서 사용자 도시 $A$로 직접 최단 경로를 이용한다.

서버가 요청 자체를 처리하거나 응답 본문을 만드는 데 걸리는 시간은 무시한다. 단, 네트워크를 통해 요청이나 응답이 이동하는 시간은 각 출발 도시와 도착 도시 사이의 최단거리만큼 걸린다.

## 웹 페이지와 결과

이 문제에서 GET 요청에 사용되는 경로는 다음 두 종류이다. 여기서 $Y$는 양의 정수인 문제 번호이다.

DB의 문제 목록에 $Y$번 문제가 존재하지 않는다면, 두 종류의 경로 모두 다음 결과를 반환한다.

```text
[ HTTP 404 ]
```

### 문제 페이지

```text
/p/Y
```

DB의 문제 목록에 $Y$번 문제가 존재한다면 이 경로의 응답 결과는 다음과 같다.

```text
[ problem Y ]
```

### 제출 현황 페이지

```text
/p/submission/Y
```

DB의 문제 목록에 $Y$번 문제가 존재한다면 이 경로의 응답 결과는 지금까지 DB에 반영된 $Y$번 문제의 제출 중 채점 시간이 짧은 순서대로 최대 $5$개의 채점 시간을 나열한 것이다.

채점 시간이 같은 제출이 여러 개라면 해당 POST 요청이 먼저 입력으로 주어진 제출이 앞선다. DB에 반영된 제출이 $k$개라면 $\min(k,5)$개의 값만 출력한다.

예를 들어 채점 시간이 $7,3,5,3,9,1$인 제출이 차례대로 DB에 반영되었다면 결과는 다음과 같다.

```text
[ 1, 3, 3, 5, 7 ]
```

아직 DB에 반영된 제출이 없다면 결과는 다음과 같다.

```text
[ ]
```

## 캐시

각 웹 서버에는 서로 독립적인 캐시 보관함이 존재한다. 모든 웹 서버의 캐시 용량은 $C$이며, 하나의 캐시 데이터는 정확히 한 칸을 차지한다.

캐시 교체 정책으로는 **LRU(Least Recently Used)** 정책을 사용한다.

각 캐시 데이터의 키는 GET 요청의 경로이며, 값은 해당 요청에 대한 응답 결과이다. `[ HTTP 404 ]`도 다른 응답과 동일하게 캐시에 저장될 수 있다.

어떤 GET 요청의 실제 처리 시작 시각이 $s$이고, 사용자가 $A$번 도시에서 다음과 같은 요청을 보냈다고 하자.

```text
GET /p/123
```

로드 밸런서는 서버 선택 규칙에 따라 웹 서버를 선택한다.

선택된 웹 서버의 캐시에 요청 경로가 존재하면 캐시 적중, 즉 `HIT`이다.

* 캐시에 저장된 결과를 그대로 사용자에게 응답한다.
* 해당 캐시 데이터는 가장 최근에 사용된 데이터가 된다.
* DB 서버에는 접근하지 않는다.

선택된 웹 서버의 캐시에 요청 경로가 존재하지 않으면 캐시 실패, 즉 `MISS`이다.

* 웹 서버는 자신과 가장 가까운 DB 서버에 요청을 보낸다.
* 실제 처리 시작 시각 $s$에 DB에 반영되어 있는 결과를 받아 사용자에게 응답한다.
* 받은 결과를 요청 경로와 함께 캐시에 저장한다.
* 캐시가 가득 찬 경우 가장 오랫동안 사용되지 않은 데이터를 하나 삭제한 뒤 새로운 데이터를 저장한다.
* 새롭게 저장된 데이터는 가장 최근에 사용된 데이터가 된다.

캐시 적중 여부의 확인, LRU 순서 변경, 캐시 저장 및 퇴출은 모두 실제 처리 시작 시각 $s$에 이루어진 것으로 본다. 따라서 이 GET 요청의 처리가 끝나기 전에는 다음 웹 요청이 같은 캐시를 조회하지 않는다.

GET 요청의 실제 처리 시작 시각부터 응답이 사용자에게 도착할 때까지 걸리는 시간은 다음과 같다.

### HIT인 경우

$$
\operatorname{dist}(A,L)
+
\operatorname{dist}(L,W)
+
\operatorname{dist}(W,A)
$$

### MISS인 경우

$$
\operatorname{dist}(A,L)
+
\operatorname{dist}(L,W)
+
2\operatorname{dist}(W,B)
+
\operatorname{dist}(W,A)
$$

여기서 $W$는 선택된 웹 서버가 위치한 도시이고, $B$는 선택된 DB 서버가 위치한 도시이다. $2\operatorname{dist}(W,B)$는 웹 서버에서 DB 서버로 요청을 보내고, DB 서버에서 웹 서버로 응답을 돌려받는 데 걸리는 시간이다.

GET 요청의 처리 종료 시각 $e$는 응답이 사용자에게 도착하는 절대 시각이다. 즉,

$$
e
=
s+
\text{실제 처리 시작 이후 응답이 도착할 때까지 걸리는 시간}
$$

이며, 출력의 `response`에는 이 값 $e$를 사용한다.

## 채점 요청

어떤 POST 요청의 실제 처리 시작 시각이 $s$이고, 사용자가 $A$번 도시에서 다음과 같은 요청을 보냈다고 하자.

```text
POST /p/Y x
```

이는 $Y$번 문제에 채점 시간이 $x$인 제출을 보낸다는 뜻이다. 모든 POST 요청의 $Y$는 DB의 문제 목록에 존재함이 보장된다.

로드 밸런서는 서버 선택 규칙에 따라 웹 서버를 선택한다. 선택된 웹 서버는 자신과 가장 가까운 채점 서버에 해당 제출을 전달한다.

선택된 웹 서버와 채점 서버가 위치한 도시를 각각 $W$, $G$라고 하자. 해당 제출이 채점 서버에 도착하는 시각은

$$
T_{\mathrm{arrive}}
=
s
+
\operatorname{dist}(A,L)
+
\operatorname{dist}(L,W)
+
\operatorname{dist}(W,G)
$$

이다. 이 시각에 제출이 채점 서버의 큐 끝에 추가되며, 해당 POST 요청의 처리 종료 시각은

$$
e=T_{\mathrm{arrive}}
$$

이다. POST 요청은 아무 응답도 출력하지 않는다.

각 채점 서버는 자신만의 FIFO 큐를 가지고 있으며, 한 번에 하나의 제출만 채점할 수 있다. 같은 채점 서버에 배정된 제출들은 채점 서버에 도착한 순서대로 큐에 들어간다. 도착 시각도 같다면 해당 POST 요청이 입력으로 주어진 순서가 앞선 제출부터 들어간다.

모든 채점 서버는 시각 $0$에 비어 있다.

어떤 제출의 채점 서버 도착 시각이 $T_{\mathrm{arrive}}$이고, 그 채점 서버에서 바로 앞 제출의 채점 완료 시각이 $T_{\mathrm{prev}}$라면 이 제출의 채점 시작 시각은

$$
T_{\mathrm{start}}
=
\max(T_{\mathrm{arrive}},T_{\mathrm{prev}})
$$

이다. 해당 채점 서버에 앞선 제출이 없다면 $T_{\mathrm{prev}}=0$으로 본다.

한 제출을 채점하는 데 걸리는 시간은 $x$이므로 채점 완료 시각은

$$
T_{\mathrm{judge}}
=
T_{\mathrm{start}}+x
$$

이다. 모든 제출의 결과는 `AC`이다.

채점이 끝나면 채점 서버는 서버 선택 규칙에 따라 자신과 가장 가까운 DB 서버에 채점 결과를 전송한다. 선택된 DB 서버가 위치한 도시를 $B$라고 하면, 결과가 DB에 반영되는 시각은

$$
T_{\mathrm{DB}}
=
T_{\mathrm{judge}}
+
\operatorname{dist}(G,B)
$$

이다.

즉, 채점이 끝난 직후 결과가 DB에 반영되는 것이 아니라, 채점 서버에서 DB 서버까지 결과가 이동하는 시간만큼 추가 지연이 발생한다. 큐 대기, 채점 및 DB 반영은 이후 웹 요청의 처리와 동시에 진행될 수 있다.

## 캐시 무효화

$Y$번 문제의 제출 결과가 시각 $T_{\mathrm{DB}}$에 DB에 반영될 때마다 제출 현황 페이지의 내용이 바뀐다.

따라서 DB가 $Y$번 문제의 제출 하나를 반영한 직후, 모든 웹 서버의 캐시에서 다음 경로를 즉시 삭제한다.

```text
/p/submission/Y
```

해당 경로를 캐시에 가지고 있지 않은 웹 서버에서는 아무 일도 일어나지 않는다.

`/p/Y`의 결과는 제출에 의해 바뀌지 않으므로 무효화하지 않는다. `[ HTTP 404 ]`가 저장된 경로 역시 문제 목록이 바뀌지 않으므로 무효화하지 않는다.

캐시 무효화에는 통신 시간이 들지 않으며, 별도의 `INVALIDATE` 요청은 주어지지 않는다.

어떤 요청의 실제 처리 시작 시각 $s_i$와 DB 반영 시각이 같다면 DB 반영과 캐시 무효화를 먼저 처리한 뒤 해당 웹 요청을 처리한다.

GET 요청의 응답 내용과 캐시 연산은 처리 시작 시각에 이미 결정된다. 따라서 GET 응답이 이동하는 도중 캐시 무효화가 발생해도 그 응답 내용은 바뀌지 않지만, 무효화된 캐시 데이터는 이후 요청에서 사용할 수 없다.

## 요청 처리

총 $Q$개의 요청이 입력 순서대로 주어진다.

직전 요청의 처리 종료 시각을 이용하여 현재 요청의 실제 처리 시작 시각 $s_i=\max(t_i,e_{i-1})$를 계산한다. 그 뒤 시각 $s_i$ 이하에 예정된 DB 반영과 캐시 무효화를 모두 처리하고 현재 요청을 처리한다.

* GET 요청은 시각 $s_i$의 캐시와 DB 상태를 기준으로 응답을 결정하고 필요한 캐시 연산을 수행한다. 응답이 사용자에게 도착하는 시각이 처리 종료 시각 $e_i$이며, $e_i$와 응답 결과를 출력한다.
* POST 요청은 제출이 채점 서버의 큐에 도착할 때까지 처리한다. 큐에 도착한 시각이 처리 종료 시각 $e_i$이며, 이후의 채점과 DB 반영은 비동기 진행된다. POST 요청은 아무것도 출력하지 않는다.

웹 요청은 서로 겹쳐 처리되지 않지만, 채점 서버의 큐 대기, 채점 및 DB 반영은 웹 요청과 동시에 진행될 수 있다.

---

## 입력

첫째 줄에 도시의 수 $N$과 도로의 수 $M$이 주어진다.

$$
2 \le N \le 200{,}000
$$

$$
N-1 \le M \le 200{,}000
$$

다음 $M$개의 줄에는 세 정수 $u,v,w$가 주어진다. 이는 $u$번 도시와 $v$번 도시를 연결하는 이동 시간 $w$의 양방향 도로가 존재한다는 뜻이다.

$$
1 \le u,v \le N,\quad u \ne v
$$

$$
1 \le w \le 10^9
$$

모든 도시는 서로 이동할 수 있음이 보장된다.

다음 줄에 로드 밸런서가 위치한 도시 $L$과 웹 서버의 수 $S$, DB 서버의 수 $D$, 채점 서버의 수 $J$, 캐시 용량 $C$가 주어진다.

$$
1 \le L \le N
$$

$$
1 \le S \le N
$$

$$
1 \le D \le 2
$$

$$
1 \le J \le 3
$$

$$
1 \le C \le 200{,}000
$$

다음 줄에 $S$개의 정수 $W_1,W_2,\dots,W_S$가 주어진다. $W_i$는 $i$번 웹 서버가 위치한 도시이다.

다음 줄에 $D$개의 정수 $B_1,B_2,\dots,B_D$가 주어진다. $B_i$는 $i$번 DB 서버가 위치한 도시이다.

다음 줄에 $J$개의 정수 $G_1,G_2,\dots,G_J$가 주어진다. $G_i$는 $i$번 채점 서버가 위치한 도시이다.

같은 종류의 서버 두 개가 같은 도시에 존재하지 않는다.

다음 줄에 DB에 저장된 문제의 수 $P$가 주어진다.

$$
1 \le P \le 200{,}000
$$

다음 줄에 서로 다른 $P$개의 정수 $R_1,R_2,\dots,R_P$가 주어진다. 이들은 DB에 존재하는 문제 번호이다.

$$
1 \le R_i \le 10^9
$$

다음 줄에 요청의 수 $Q$가 주어진다.

$$
1 \le Q \le 200{,}000
$$

다음 $Q$개의 줄에는 다음 두 종류 중 하나의 요청이 주어진다.

```text
t GET A path
t POST A /p/Y x
```

* $t$는 사용자가 요청을 보낸 시각이다.
* $A$는 요청을 보낸 사용자가 위치한 도시이다.
* GET 요청의 `path`는 `/p/Y` 또는 `/p/submission/Y` 형식이다.
* $Y$는 문제 번호를 나타내는 양의 정수이다.
* POST 요청의 $x$는 제출의 채점 시간이다.

요청 시각은 입력에서 엄격히 증가한다. 단, 앞선 요청의 처리가 끝나지 않았다면 실제 처리 시작 시각은 입력 시각 $t$보다 늦을 수 있다.

$$
1 \le t \le 10^{18}
$$

$$
1 \le A \le N
$$

$$
1 \le Y \le 10^9
$$

$$
1 \le x \le 10^9
$$

모든 POST 요청에 등장하는 문제 번호 $Y$는 DB의 문제 목록에 존재함이 보장된다.

모든 요청에 등장하는 경로 문자열 길이의 합은 $3{,}000{,}000$ 이하이다.

---

## 출력

각 GET 요청에 대해 다음 형식으로 한 줄을 출력한다.

```text
response result
```

* `response`는 해당 GET 요청의 실제 처리 시작 시각에 네트워크 지연 시간을 더한 값, 즉 응답이 사용자에게 도착하면서 요청 처리가 끝나는 절대 시각이다.
* `result`는 요청한 경로의 응답 결과이다.

존재하지 않는 문제 번호에 대한 두 종류의 GET 요청 결과는 다음과 같다.

```text
[ HTTP 404 ]
```

존재하는 문제의 `/p/Y`에 대한 결과는 다음 형식이다.

```text
[ problem Y ]
```

존재하는 문제의 `/p/submission/Y`에 대한 결과는 다음 형식이다.

```text
[ a, b, c, d, e ]
```

DB에 반영된 제출이 $5$개보다 적다면 존재하는 값만 출력하며, 하나도 없다면 `[ ]`를 출력한다.

POST 요청에 대해서는 아무것도 출력하지 않는다.

모든 실제 처리 시작 시각, 요청 처리 종료 시각, 응답 도착 시각, 채점 서버 도착 시각, 채점 시작 시각, 채점 완료 시각 및 DB 반영 시각은 64비트 부호 있는 정수 범위 안에 들어온다.

```text
4 4
1 2 1
2 3 1
3 4 1
1 4 10
2 2 1 1 2
1 4
3
2

14 GET 4 /p/submission/123
15 GET 4 /p/submission/123

```

```text
7 [ problem 123 ]
13 [ HTTP 404 ]
25 [ ]
31 [ 5 ]
35 [ 5 ]
41 [ HTTP 404 ]
```

## 예제 설명

DB의 문제 목록에는 $123$번 문제만 존재한다.

첫 번째 요청의 입력 시각은 $1$이고 앞선 요청이 없으므로 실제 처리 시작 시각도 $1$이다. 이 GET 요청은 $1$번 웹 서버로 전달된다. 캐시에 `/p/123`이 없으므로 DB 서버를 거쳐 결과 `[ problem 123 ]`을 가져온다. 실제 처리 시작 이후 응답이 도착할 때까지 걸리는 시간은

$$
\operatorname{dist}(1,2)
+
\operatorname{dist}(2,1)
+
2\operatorname{dist}(1,3)
+
\operatorname{dist}(1,1)
=6
$$

이다. 따라서 응답 도착 시각이자 첫 번째 요청의 처리 종료 시각은 $1+6=7$이다.

두 번째 요청의 입력 시각은 $2$이지만 첫 번째 요청이 시각 $7$에 끝나므로 실제 처리 시작 시각은

$$
\max(2,7)=7
$$

이다. $999$번 문제는 DB의 문제 목록에 존재하지 않으며, `/p/999`는 캐시에 없으므로 `MISS`이다. 처리 시간은 $6$이므로 응답 도착 시각은 $7+6=13$이고 결과는 `[ HTTP 404 ]`이다.

세 번째 요청은 입력 시각 $3$의 POST이지만 실제로는 두 번째 요청이 끝난 시각 $13$부터 처리된다. 이 요청은 $4$번 웹 서버와 $2$번 도시에 있는 채점 서버를 선택한다. 제출이 채점 서버에 도착하는 시각은

$$
13
+
\operatorname{dist}(4,2)
+
\operatorname{dist}(2,4)
+
\operatorname{dist}(4,2)
=13+2+2+2=19
$$

이다. 이 시각에 POST 요청의 웹 처리가 끝나며, 제출은 채점 서버의 큐에 들어간다.

채점 서버는 비어 있으므로 시각 $19$부터 채점을 시작한다. 채점 시간이 $5$이므로 채점 완료 시각은 $24$이다. 채점 서버는 $3$번 도시에 있는 DB 서버로 결과를 전송하며, $\operatorname{dist}(2,3)=1$이므로 결과가 DB에 반영되는 시각은 $24+1=25$이다.

네 번째 요청의 입력 시각은 $4$이지만 POST 요청이 끝난 시각 $19$부터 실제 처리를 시작한다. 이 시각에는 아직 채점 결과가 DB에 반영되지 않았으므로 `/p/submission/123`의 결과는 `[ ]`이다. 캐시 `MISS`의 처리 시간은 $6$이므로 응답은 시각 $25$에 도착한다.

이 GET 요청의 응답 내용과 캐시 연산은 실제 처리 시작 시각 $19$에 이미 결정되었으므로, 응답이 이동하는 도중인 시각 $25$에 채점 결과가 DB에 반영되더라도 이 응답은 `[ ]`로 유지된다. 시각 $25$에는 DB 반영과 함께 모든 웹 서버의 `/p/submission/123` 캐시가 무효화된다.

다섯 번째 요청의 입력 시각은 $14$이지만 실제 처리 시작 시각은 $25$이다. 같은 시각에 예정된 DB 반영과 캐시 무효화를 먼저 처리하므로 이 요청은 캐시 `MISS`이며 결과 `[ 5 ]`를 받는다. 응답 도착 시각은 $25+6=31$이다.

여섯 번째 요청의 입력 시각은 $15$이지만 실제 처리 시작 시각은 $31$이다. 같은 웹 서버의 캐시에 `/p/submission/123`이 있으므로 `HIT`이다. 처리 시간은

$$
\operatorname{dist}(4,2)
+
\operatorname{dist}(2,4)
+
\operatorname{dist}(4,4)
=2+2+0=4
$$

이므로 응답 도착 시각은 $31+4=35$이고 결과는 `[ 5 ]`이다.

마지막 요청의 입력 시각은 $20$이지만 실제 처리 시작 시각은 $35$이다. $999$번 문제는 존재하지 않고, 선택된 $2$번 웹 서버에는 `/p/submission/999`가 캐시되어 있지 않으므로 `MISS`이다. 결과는 `[ HTTP 404 ]`이고 응답 도착 시각은 $35+6=41$이다.
